# Observability Module

Monitoring, alerting, and logging for the EKS cluster.

## Metrics, dashboards, and alerts — in-cluster only

Everything runs inside the cluster via the `kube-prometheus-stack` Helm release
(`monitoring` release, `monitoring` namespace). Values are rendered from
[`prometheus-values.yaml.tftpl`](./prometheus-values.yaml.tftpl).

| Component | Notes |
|---|---|
| **Prometheus** | 30d / 50GB retention, 50Gi `gp3-monitoring` PVC, IRSA service account, scrapes annotated pods + the Redis exporter. |
| **Grafana** | Persisted (10Gi `gp3-monitoring`), admin credentials generated by Terraform into the `grafana-admin-credentials` secret, `Microservices` and `Infrastructure` dashboard folders. |
| **AlertManager** | 10Gi PVC, routes all alerts to an SNS topic that emails `alert_email_address`. |
| **node-exporter / kube-state-metrics / Prometheus Operator** | Enabled, with the upstream `defaultRules` (etcd, kube-proxy, and kube-scheduler rules disabled — not applicable to managed EKS). |

## Access — private, port-forward only

The monitoring stack is **not exposed publicly**. There is no ingress and no
ALB; Grafana, Prometheus, and Alertmanager are ClusterIP services reachable
only from inside the cluster.

Reach each UI locally with `kubectl port-forward`, then open the URL:

```bash
# Grafana -> http://localhost:3000
kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80

# Prometheus -> http://localhost:9090
kubectl port-forward -n monitoring svc/monitoring-kube-prometheus-prometheus 9090:9090

# Alertmanager -> http://localhost:9093
kubectl port-forward -n monitoring svc/monitoring-kube-prometheus-alertmanager 9093:9093
```

Grafana logs in as `admin`; get the generated password with:

```bash
kubectl get secret grafana-admin-credentials -n monitoring   -o jsonpath='{.data.admin-password}' | base64 -d
```

The `port_forward_commands` and `grafana_access_info` outputs print these same
commands with the right namespace already filled in.

> This is separate from the application's frontend ALB ingress, which is
> unchanged and still serves the storefront publicly.

Application-level alert rules are **not** defined here — they ship with the app
in `helm/online-boutique/templates/prometheusrules.yaml`.

### No external metrics backend

Prometheus has **no `remoteWrite` targets**. Grafana Cloud remote write was
removed from this project for now, so all metrics stay in the cluster and
nothing is shipped to a SaaS backend. Re-adding it later means:

1. A `remoteWrite` block in `prometheus-values.yaml.tftpl`.
2. A Kubernetes secret holding the basic-auth credentials.
3. Variables for the endpoint URL and credentials — supplied via
   `TF_VAR_*` env vars or a `.tfvars` file that is **not** committed, never
   hardcoded in `terraform.tfvars`.

> The in-cluster Grafana above is unrelated to Grafana Cloud and is still fully
> deployed.

## Logs

CloudWatch via the `amazon-cloudwatch-observability` EKS add-on (OTel
auto-instrumentation disabled). Four log groups — application, dataplane, host,
performance — at 7-day retention.

## AWS-managed service alarms

CloudWatch alarms on RDS (CPU, free storage, connections, freeable memory),
ElastiCache Redis (CPU, memory, evictions), and the ALB (5xx, target 5xx,
unhealthy targets). All notify the same SNS topic as AlertManager.

## Useful outputs

`port_forward_commands`, `monitoring_local_urls`, `grafana_access_info`,
`grafana_admin_password` (sensitive), and a set of `kubectl` helper commands —
see [`outputs.tf`](./outputs.tf).
